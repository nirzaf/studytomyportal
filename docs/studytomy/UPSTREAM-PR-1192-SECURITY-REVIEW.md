## Evidence and review notes

### Outbound SSRF protection

The current local guard validates DNS results and checks the actual peer after an `httpx` request. However, `link_preview.py` and `webhooks/dispatch.py` construct ordinary `httpx.AsyncClient` instances without a pinned transport. The webhook POST is initiated before `assert_connected_peer_allowed` runs. A DNS change between the initial check and socket resolution can therefore send a request to an address that was not approved before the after-the-fact check rejects the response. The verified-domain SSL check in `orgs/custom_domains.py` has the same time-of-check/time-of-use gap: it validates the name, then opens a TLS socket using the hostname and lets the socket resolve it again. The PR's `connect_validated` path connects to a guarded IP for this probe, while `pinned_transport` does the equivalent for `httpx`; peer validation remains a backstop. This is the strongest direct security gap in the reviewed changes.

### Media demuxer restriction

The current protocol whitelist permits local-file and pipe protocols, while there is no demuxer allowlist. PR #1192 adds a single-file media format allowlist and applies it to the shared FFmpeg/FFprobe input arguments. This is relevant to user-supplied uploads and imports. Adapt the behavior only with regression cases for supported containers, HLS/concat inputs, and generated output formats so existing media workflows remain intact.

PR source: [video processing at reviewed head](https://raw.githubusercontent.com/learnhouse/learnhouse/cc3d4a03abd1a2e67322fef0f9c78c0e70012dd4/apps/api/src/services/utils/video_processing.py). Local seam: `apps/api/src/services/utils/video_processing.py` and its consumers in `apps/api/src/services/utils/hls_transcode.py`.

### Service-key placeholders and JWT secret handling

The local boards dependency compares the request header with `os.getenv("COLLAB_INTERNAL_KEY", "")` directly. Empty/unset values are rejected, but a published non-empty example value would be accepted at the API boundary. The CSRF middleware also accepts non-empty configured values for its internal-header exemption without filtering examples. The collab process rejects three older examples, but the API and collab sides do not share one validation rule. PR #1192 adds a shared-secret filter in API config, uses it for the boards route and CSRF exemptions, and aligns collab placeholder handling. The reviewed PR intentionally warns rather than refuses for the example JWT secret because the key also protects stored encrypted values; that warning is not evidence that a real deployed secret is safe. Do not print, rotate or otherwise modify any configured secret during this review.

### Self-hosted inbox proof

In OSS mode, the local user-creation path marks email signups verified without an email proof round trip. The current Google pre-hijack guard removes a password only when `email_verified` is false (or the account has the special admin-created password condition). An attacker who pre-creates a self-hosted account for another person's address can therefore leave a password that the later mailbox owner does not displace through the existing checks. The local reset path drops SSO links only when `email_verified` is false; SSO itself is an Enterprise hook and is not enabled by the Community Edition target. PR #1192 uses the existing `email_verified_at` field as a proof marker for self-hosted signups, and applies one account-claim helper to Google, magic-link and reset-code proof. No new schema is shown in the PR file list, but compatibility with old application code and all auth entry points must be verified before adoption.

PR sources: [account claim helper](https://raw.githubusercontent.com/learnhouse/learnhouse/cc3d4a03abd1a2e67322fef0f9c78c0e70012dd4/apps/api/src/services/auth/utils.py), [inbox-proof marker](https://raw.githubusercontent.com/learnhouse/learnhouse/cc3d4a03abd1a2e67322fef0f9c78c0e70012dd4/apps/api/src/services/users/users.py), [password reset](https://raw.githubusercontent.com/learnhouse/learnhouse/cc3d4a03abd1a2e67322fef0f9c78c0e70012dd4/apps/api/src/services/users/password_reset.py). Local seams: `apps/api/src/services/users/users.py`, `apps/api/src/services/auth/utils.py`, `apps/api/src/services/users/password_reset.py`, `apps/api/src/security/auth.py`.

### Follow-up gap inside the PR

The PR's account-claim helper revokes existing sessions only when it removes an untrusted password, while it removes unverified SSO links for any untrusted account. If an untrusted SSO link has already minted a session that remains valid independently of that link, that session may survive link removal until token expiry. This is a **potential, unverified** gap: verify the Enterprise hook and session semantics and add a targeted test before treating it as a confirmed vulnerability or changing the implementation.

The collab validator also places `replace-with-at-least-32-random-characters` in a warn-only set used for both `LEARNHOUSE_AUTH_JWT_SECRET_KEY` and `COLLAB_INTERNAL_KEY`. API `shared_secret_from_env` rejects this value when used as a service key, but the collab process still starts with it. This is fail-closed for the API call path but can leave a broken collaboration service, and the same value remains unsafe as a JWT secret. Keep the JWT warning behavior separate from strict service-key rejection in any adaptation; this is a **configuration-consistency follow-up**, not evidence of an API authentication bypass in the reviewed PR.

## Compatibility, verification and adoption

- The PR's pinned transport reaches into private `httpx`/`httpcore` attributes (`transport._pool` and `_network_backend`). It fails closed when the expected pool shape changes, but requires a version-locked compatibility test on the fork's actual dependency set. The current API pins `httpx==0.28.1`; compatibility with the resolved `httpcore` version is not established by this review. The GitHub PR page reports 26 checks passed at merge; that is upstream evidence only, not verification against this fork.
- The reviewed changes do not require an independent service or database. The inbox-proof behavior reuses an existing user field, but needs PostgreSQL-backed auth regression coverage and rollback compatibility analysis.
- Suggested focused checks before any implementation approval: DNS rebinding cannot connect to a private peer for link previews, webhooks or the custom-domain SSL probe, and webhook data is not sent before pin validation; redirect-by-redirect link-preview validation; media playlist/concat cannot read arbitrary local files while supported upload formats remain functional; each published internal-key placeholder is rejected by both API and collab, including the CSRF exemption path; self-hosted email-signup accounts lose unproven credentials on each supported inbox-proof route; and existing sessions are revoked when untrusted auth methods are removed.
- **Implementation option:** selectively adapt the four changes in the table after reviewing the exact diff against this fork. Do not merge or cherry-pick the five-commit PR wholesale. No code from PR #1192 was adopted in this review.
- **Rollout / rollback:** first validate in an isolated staging environment with synthetic accounts and test media. These appear to be application/configuration changes rather than schema changes; confirm that against the exact diff before implementation. Roll back application code if checks fail. Inventory deployments using published example secrets without exposing values; never force key rotation because of this review.
- **Decision:** `DEFER` adoption pending explicit Stage B approval of the precise files and scope. **Priority:** P1 for SSRF, internal-key validation and inbox proof; P2 for media demuxer restriction. **Owner:** designated Studytomy decision-maker not identified. **Approval:** `APPROVAL PENDING`.
